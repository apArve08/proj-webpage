4. The State Machine (Folder States)

The whole design is a state machine. A specification exists in exactly one of five folder states, and every workflow exists to move it between them safely.

Pending Distribution → Active Spec → Temporarily Inactive → Obsolete Spec → Archive Spec
Type of Folder Definition Publish to MES
Pending Distribution FolderPending PC to distribute the specNo
Active Spec FolderContains all active spec for operational use.Yes
Temporarily Inactive Spec FolderContains spec that are temporarily suspended from use but not fully obsolete.No
Obsolete Spec FolderContains spec that are no longer use / old revision of specNo
Archive Spec FolderContains all historical revision of spec for discontinued code and retained for long term record-keeping.No

7. Flow B — Temporary Specs

No approval required. Maximum 14-day validity. Overrides original spec, then reverts automatically.

Lifecycle Steps

  1. Search existing spec ➔ Select machine no / type.
  2. Retrieve latest revision ➔ Upload temp spec.
  3. Set validity period (max 14 days) ➔ Validate inputs.
  4. Activate: Temp spec moves to Active folder.
  5. Original spec moved to Temporarily Inactive folder.
  6. Temp spec published to MES production view.

8. Flow C — Revision (The Cleanup Flow)

Must gracefully handle the scenario where a Temporary Spec is active at the exact moment a new permanent revision is released.

Path: New Revision Approved → Pending → Flow PC Gate → New Spec moves to Active folder.

Logic Branch: Is a Temporary Spec currently active?

YES (Conflict)

  1. Inactivate Temp Spec → Move Temp to Obsolete.
  2. Inactivate Previous Original → Move from Temp Inactive to Obsolete.

NO (Standard)

  1. Inactivate Previous Original → Move from Active to Obsolete.

Final Step: Notify related production and publish new revision to MES.

9. Data Model (SharePoint Lists)

Three lists. No Dataverse (confirmed, to avoid premium licensing overhead).

1. SpecRegister

Tracks current state of specs.

  • Title: {TyreCode}-{Rev}
  • Revision / Status
  • FolderState
  • FileItemId: SP Item ID (what MES resolves)
  • SupersedesId: Pointer to previous rev.

2. SpecAudit

Append-only event log.

  • CorrelationId: GUID grouping transactions
  • Action: Approved, Released, Held, Obsoleted...
  • ActorUPN: The real person (passed in)
  • Result: Success / Failure
  • Details: JSON payload config

3. SpecConfig

Operational parameters.

  • Reminder interval days
  • PC recipient groups
  • Folder paths
  • Notification text templates

Kept out of flow expressions to allow updates without editing code.

11. Golden Build Rules

Five constraints that shape the implementation.

1
Register first, folder second. Every state change writes to SpecRegister before the file moves. MES resolves FileItemId, never a folder path.
2
Actor is passed in, never inferred. Flows run as service accounts, so "Created By" is meaningless. The real user UPN comes in as a parameter.
3
One CorrelationId per transaction. Generated in the parent flow and threaded through every child call for end-to-end tracing.
4
Failures are logged explicitly. Each action group sits in a Scope with a parallel failure Scope writing Result = Failure and setting the register row to NeedsAttention.
5
No true transactions exist. Any flow that can inadvertently leave two specs Active must have a rigid failure branch that flags and alerts admins immediately.
